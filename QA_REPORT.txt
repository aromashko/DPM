2. КРИТИЧЕСКИЕ БАГИ (BLOCKER)
===============================================================================

BUG-001: ttf-mscorefonts-installer не установится в Docker
───────────────────────────────────────────────────────────────────────────────
Серьёзность: CRITICAL
Файл: Dockerfile, строки 11-15

Проблема:
  Пакет ttf-mscorefonts-installer находится в репозитории Debian `contrib`,
  а python:3.13-slim по умолчанию содержит только `main`. Установка завершится
  ошибкой: "E: Package 'ttf-mscorefonts-installer' has no installation candidate"

Воспроизведение:
  docker build -t docx-worker .
  → E: Package 'ttf-mscorefonts-installer' has no installation candidate

Исправление:
  Добавить contrib в sources перед установкой:
  RUN echo "deb http://deb.debian.org/debian bookworm contrib" >> /etc/apt/sources.list

───────────────────────────────────────────────────────────────────────────────

BUG-002: Временные файлы не удаляются при ошибке LibreOffice
───────────────────────────────────────────────────────────────────────────────
Серьёзность: HIGH
Файл: worker.py, строки 108-154

Проблема:
  Если subprocess.run() выбросит исключение (timeout, OSError) или LibreOffice
  завершится с ошибкой, временный каталог /tmp/docx_worker_* и файлы в нём
  останутся навсегда. При длительной работе это приведёт к заполнению диска.

Исправление:
  Использовать tempfile.TemporaryDirectory() с контекстным менеджером,
  либо try/finally для очистки.

───────────────────────────────────────────────────────────────────────────────

BUG-003: LibreOffice может зависнуть из-за блокировки профиля
───────────────────────────────────────────────────────────────────────────────
Серьёзность: HIGH
Файл: worker.py, строки 115-128

Проблема:
  LibreOffice использует ~/.config/libreoffice как user profile. Если процесс
  не был корректно завершён, остаётся файл .lock, и последующие вызовы
  headless зависают навсегда (timeout=120 не поможет — процесс висит).

Исправление:
  Добавить флаг -env:UserInstallation=file:///tmp/lo_profile_{uuid}
  для изоляции профиля каждого вызова.

MAJOR-002: import time внутри цикла while True
───────────────────────────────────────────────────────────────────────────────
Серьёзность: LOW
Файл: worker.py, строки 367 и 379

Проблема:
  `import time` выполняется при каждой итерации цикла переподключения.
  Хотя Python кэширует модули, это нарушение PEP 8 — импорты должны быть
  в начале файла.

Исправление: перенести `import time` в блок импортов (строка 8-16).

───────────────────────────────────────────────────────────────────────────────

MAJOR-003: Отсутствие graceful shutdown
───────────────────────────────────────────────────────────────────────────────
Серьёзность: MEDIUM
Файл: worker.py

Проблема:
  При SIGTERM (docker stop) connection к RabbitMQ не закрывается корректно.
  Сообщения, находящиеся в обработке, могут быть потеряны или обработаны
  повторно (зависит от состояния ack).

Исправление:
  Зарегистрировать signal handler для SIGTERM/SIGINT, который закроет
  connection и channel перед выходом.

───────────────────────────────────────────────────────────────────────────────

MAJOR-004: docker-compose.yml — устаревший синтаксис
───────────────────────────────────────────────────────────────────────────────
Серьёзность: LOW
Файл: docker-compose.yml

Проблемы:
  1. `version: "3.8"` — deprecated в Docker Compose v2+ (игнорируется)
  2. `container_name` — мешает масштабированию (docker-compose up --scale)
  3. Нет healthcheck для worker

4. ПРОБЛЕМЫ БЕЗОПАСНОСТИ
===============================================================================

SEC-001: Credentials в логах при старте
───────────────────────────────────────────────────────────────────────────────
Серьёзность: LOW
Файл: worker.py, строки 329-338

Проблема:
  При старте логируется rabbitmq_host и rabbitmq_port. Хотя пароли не
  логируются, в некоторых конфигурациях это может быть нежелательно.
  Рекомендуется log_level=DEBUG не использовать в production.

SEC-002: Нет валидации входящих сообщений
───────────────────────────────────────────────────────────────────────────────
Серьёзность: MEDIUM
Файл: worker.py, handle_message()

Проблема:
  Нет проверки размера сообщения. Злоумышленник может отправить огромное
  сообщение (например, 1GB base64), что приведёт к OOM.
  Нет проверки корректности base64 (может упасть с исключением).

Рекомендация:
  - Ограничить размер сообщения через basic_consume arguments
  - Добавить валидацию обязательных полей
  - Обернуть base64.b64decode в try/except

SEC-003: Отсутствие .dockerignore
───────────────────────────────────────────────────────────────────────────────
Серьёзность: LOW

Проблема:
  Без .dockerignore в образ попадают .env, .git, node_modules и другие
  ненужные файлы, увеличивая размер образа и потенциально раскрывая секреты.

===============================================================================
5. ПРОБЛЕМЫ НАДЁЖНОСТИ
===============================================================================

REL-001: Нет exponential backoff при переподключении
───────────────────────────────────────────────────────────────────────────────
Серьёзность: MEDIUM
Файл: worker.py, строки 362-380

Проблема:
  При потере соединения worker ждёт фиксированные 5 секунд и пытается
  переподключиться. Если RabbitMQ недоступен долго, это создаёт постоянную
  нагрузку на сеть и логи.

Рекомендация:
  Реализовать exponential backoff: 5s → 10s → 20s → 40s → max 60s.

REL-002: Нет ограничения на размер очереди ошибок
───────────────────────────────────────────────────────────────────────────────
Серьёзность: LOW

Проблема:
  Если воркер начнёт массово ошибаться (например, неверный формат шаблона),
  ERROR_QUEUE будет расти бесконечно.
